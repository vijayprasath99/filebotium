# Audit: Rename Workspace & Matching Engine (specs/02) + Format Expression Engine (specs/03)

## 1. Methodology

Read in full: legacy Swing sources `net.filebot.ui.rename.{RenamePanel,RenameModel,MatchModel,RenameList,MatchAction,RenameAction,ConflictDialog,ValidateDialog,FormatDialog,BindingDialog,PresetEditor,HistoryDialog}`, `net.filebot.StandardRenameAction`; React `RenameWorkspace.tsx`, `MatchTableContainer.tsx`, `MatchTable.tsx`, `FormatEditorModal.tsx`, `EpisodeBindingsModal.tsx`, `BindingPicker.tsx`; Spring Boot `RenameWorkspaceController/ServiceImpl`, `FormatController`, `FormatExpressionEngineServiceImpl` (both controller+impl, not just interfaces). Cross-referenced every `JButton`/`Action`/`KeyStroke`/context-menu found in the legacy source against the React component tree and then against the Spring Boot call it would need to reach. `net.filebot.format.MediaBindingBean` (1128 lines) and `ExpressionFormat` were spot-checked, not read in full — flagged where that matters.

## 3. Ambiguous / undocumented JavaFX behavior (not to be guessed at)

- **AMB-1 (ConflictStrategy.AUTO_RENAME):** specs/00 and specs/02 define `ConflictStrategy` as `OVERWRITE | FAIL | SKIP | AUTO_RENAME`. Nothing in the legacy `ConflictDialog`/`RenameAction`/`ValidateDialog` implements an "auto-rename with a numeric counter" behavior — the only two resolutions offered to the user are "Continue" (skip the conflicting file — closest existing analog to `SKIP`) and "Override" (trash the existing destination file, then proceed — closest analog to `OVERWRITE`). There is no legacy `FAIL`-the-whole-batch behavior distinct from the user cancelling the whole dialog. `AUTO_RENAME` appears to be an invented enum value with no legacy precedent found anywhere in `net.filebot.ui.rename` or `net.filebot.StandardRenameAction`. Implementers should not silently implement an "append (1), (2), ..." counter scheme as if it were legacy behavior — confirm intent with product owner before building it.
- **AMB-2 (RenameModel per-type formatter persistence keys):** `RenamePanel` persists **four independent format expressions** (`rename.format.episode`, `rename.format.movie`, `rename.format.music`, `rename.format.file`) plus a separate "last mode used" preference, and applies the correct one automatically based on the *runtime type* of each match's bound object (`RenameModel.getFormatter(match)` picks the first formatter whose `canFormat()` matches — Episode/Movie/AudioTrack/File in that priority order). The current React/Spring Boot design instead threads one single global `formatExpression` string through the whole app (`AppShell` state). Whether the intended target design is "one universal expression the user must manually keep in sync across content types" or "four independently-persisted per-type expressions applied automatically like legacy" is not stated anywhere in specs/02 or specs/03 — this needs an explicit product decision, not an assumption, since it changes the `AppSettingsDto` shape (`tvFormat`/`movieFormat`/`musicFormat`/`animeFormat` already exist there, suggesting per-type was intended, but nothing in the Rename workspace ever reads them).
- **AMB-3 (native shell rename):** `RenameAction.actionPerformed()` branches on `useNativeShell() && NativeRenameAction.isSupported(action)` to use a platform-native (macOS/Windows shell-integrated, presumably trash-integrated / progress-native) rename path instead of the plain Java NIO path. It's unclear whether the Spring Boot backend (headless, no native shell integration surface) is expected to ever replicate this, or whether `StandardRenameAction`-only is the accepted target behavior for the web/Electron port. Flagging rather than assuming "not needed."

## 4. Reuse opportunities

- **`net.filebot.StandardRenameAction`** — already correctly reused by `RenameWorkspaceServiceImpl.executeRename()` for the actual move/copy/link operation. Good precedent; extend this same direct-reuse approach to close RF-03/RF-04 rather than reimplementing.
- **`net.filebot.HistorySpooler` / `net.filebot.History`** — directly portable/callable from `RenameWorkspaceServiceImpl.executeRename()` to fix RF-03: call `HistorySpooler.getInstance().append(renameLog.entrySet())` (or the Spring `HistoryService` equivalent, backed by the same class) immediately after each successful rename, exactly as `RenameAction.java:142` does. This is a small, low-risk change with high payoff (unblocks Undo/Rollback end-to-end).
- **`net.filebot.similarity.Matcher` + `net.filebot.similarity.EpisodeMetrics().matchFileSequence()`** (used by `MatchAction.java:44-49`) and the per-mode matchers `EpisodeListMatcher`/`MovieMatcher`/`MusicMatcher`/`AutoDetectMatcher` (`net.filebot.ui.rename`) together with `WebServices` (`net.filebot.WebServices.getEpisodeListProviders()`/`getMovieIdentificationServices()`/`getMusicIdentificationServices()`) are the exact legacy call graph needed to fix RF-01/RF-02. These are plain Java (not Swing-coupled beyond passing a `Window` for progress/dialogs, which can be stubbed/removed for a headless service), and are the highest-value, lowest-risk porting target in the entire Rename area — this single change fixes the app's core matching feature.
- **`net.filebot.format.ExpressionFormat` / `MediaBindingBean`** — already correctly reused for expression compilation/evaluation (`evaluateExpression`, `validateExpressionSyntax`). To fix RF-15, replace the hardcoded 8-entry list in `getAvailableBindings()` with reflective introspection of `MediaBindingBean`'s public getters (legacy's own `BindingDialog`/`FormatDialog` resource bundles, e.g. `FormatDialog.properties`, likely already enumerate the canonical binding catalog and example expressions per mode — worth locating and reusing those resource bundles directly instead of hand-authoring a new list).
- **`net.filebot.ui.rename.ConflictDialog.check()` / `ValidateDialog.validate()`** — the *validation logic* inside these classes (duplicate-destination detection, illegal-character detection via `isInvalidFilePath`) is decoupled enough from Swing rendering to extract into a plain service method returning a list of conflicts/issues; only the dialog presentation is Swing-specific. Porting the logic (not the dialog) directly closes most of RF-04's data-integrity risk.
