## 3. Ambiguous / undocumented JavaFX (Swing) behavior

**3.1 No per-row context menu exists in the legacy code (correcting the task brief's hypothesis).**
`Grep` of `net/filebot/ui/sfv/**` for `JButton|JMenuItem|JPopupMenu|addActionListener|MouseListener|MouseAdapter|getComponentPopupMenu|setComponentPopupMenu` returns **only** 4 hits, all in `SfvPanel.java` (the `import javax.swing.JButton;` plus the 3 toolbar `JButton` instantiations at lines 67-69: Load, Save, Clear). There is no `JPopupMenu`, no `JMenuItem`, no `MouseListener`/`MouseAdapter`, and no `addActionListener` call anywhere in the package (all actions use Swing `Action` objects bound directly to buttons/keystrokes, e.g. `installAction(this, KeyStroke.getKeyStroke(KeyEvent.VK_DELETE, 0), removeAction)`). So: no "recompute single row," no "open file," no "reveal in folder" right-click action exists to port — GAP-16 above is the accurate characterization (missing DELETE-key multi-row remove), not a missing context menu.

**3.2 `WARNING` row state is effectively dead for non-CRC32 hash types.**
`ChecksumRow.getVerdict()` (`ui/sfv/ChecksumRow.java:126-146`) only raises `WARNING` when `checksum.length() == embeddedChecksum.length()`. `VerificationUtilities.EMBEDDED_CHECKSUM` (`hash/VerificationUtilities.java:20-21`) matches **exactly 8 hex digits** (`\p{XDigit}{8}`). MD5 (32 chars), SHA-1 (40 chars), SHA-256 (64 chars) digests can never equal 8 characters, so the embedded-checksum `WARNING` comparison is only ever reachable when the active hash type is CRC32 (`SFV`). This looks like a long-standing legacy quirk/limitation rather than intentional design, but it changes how "faithful" a port needs to be — a literal port would also only support `WARNING` for CRC32.

**3.3 Dynamic thread-pool sizing heuristic has no documented rationale.**
`ChecksumComputationExecutor.getPreferredPoolSize()` (`ui/sfv/ChecksumComputationService.java:109-116`) uses `Math.max(1, Math.round(Math.sqrt(threadPoolSize) + Math.log10(getQueue().size()) - 1))`, justified only by an inline comment with example numbers ("50 files ~ 1 thread, 200 files ~ 2 threads..."). There's no reference to *why* this specific formula was chosen (vs. e.g. a fixed pool = `availableProcessors()`, as spec §00's `hashingExecutor` bean actually proposes). A literal 1:1 port of this heuristic is probably not worth preserving; the spec's simpler fixed-size `ThreadPoolTaskExecutor` is a reasonable replacement, but this divergence should be a conscious decision, not an accidental omission (currently it's the latter, since no executor exists at all — GAP-05).

**3.4 Multi-column / multi-root comparison is core UX, not a peripheral feature.**
The entire `ChecksumTableModel` design (dynamic columns keyed by dropped root, `getColumnIndex(ChecksumCell)`, `isVerificationColumn`) exists specifically to let users diff hashes across several sources at once. This is arguably the single most distinctive feature of the legacy SFV panel (beyond simple SFV-file verification) and is completely absent from both the React data model and the target DTO shape defined in spec §00/§06 (`ChecksumEntryDto` only carries one `expectedHash` + one `calculatedHash`). Worth flagging to the spec authors as a scope decision to confirm explicitly, rather than an accidental gap — but as implemented, it is a gap (GAP-13).

**3.5 `BUFFER_SIZE` confirmed at exactly 64KB, not "64KB-256KB" as spec text claims.**
`net.filebot.util.FileUtilities.BUFFER_SIZE = 64 * 1024` (`util/FileUtilities.java:767`) is the single constant used by both `ChecksumComputationTask` (via static import) and `VerificationUtilities.computeHash`. The spec's "typically 64KB - 256KB buffer sizes" (§A.1) appears to be an approximation/hallucination — there is only one fixed 64KB buffer size in the legacy codebase, no configurable range.

## 4. Reuse opportunities

Specific `net.filebot.hash.*` classes `ChecksumServiceImpl` should call directly instead of reimplementing (or, currently, instead of doing nothing):

1. **`net.filebot.hash.HashType`** (`hash/HashType.java`) — `newHash()` returns the correct `Hash` implementation per algorithm (`ChecksumHash(new CRC32())` for CRC32/SFV, `MessageDigestHash("MD5"/"SHA-1"/"SHA-256"/"SHA3-384")` for the rest). `ChecksumServiceImpl.startVerificationTask` should map `backend.domain.HashType` → `net.filebot.hash.HashType` and call `.newHash()` per file instead of implementing/using nothing (GAP-01/06). This also automatically gets buffer-size-correct streaming behavior for free if combined with #2.

2. **`net.filebot.hash.VerificationUtilities.computeHash(File, HashType)`** (`hash/VerificationUtilities.java:85-107`) — already does exactly the streaming-64KB-buffer hash-and-digest logic the backend needs (`hash.update(buffer, 0, len)` in a loop, `InterruptedException` check for cancellability). This single static method is essentially the whole missing implementation of GAP-01/05/06 for the *synchronous, single-file* case; wrapping N calls to it in a `CompletableFuture`/`ExecutorService` (per spec §00's `hashingExecutor` bean) would close GAP-01, GAP-05, and GAP-06 simultaneously with minimal new code.

3. **`net.filebot.hash.VerificationUtilities.getHashType(File)`** (`hash/VerificationUtilities.java:69-75`) — resolves the correct `HashType` (and thus correct `VerificationFormat`) from a verification file's extension via `HashType.getFilter()`. `ChecksumServiceImpl.parseVerificationFile` should call this instead of hardcoding `new SfvFormat()` (GAP-07); this one substitution fixes both the silent-empty-parse bug and the hardcoded `HashType.CRC32` on every returned DTO.

4. **`net.filebot.hash.VerificationFileReader`** — already reused correctly by `parseVerificationFile` (good, keep) and could also be reused by a "detect + resolve missing files" pass to implement GAP-10 (spec §D.2), since it already yields `Entry<File, String>` pairs whose `File.exists()` can be checked against the target directory.

5. **`net.filebot.hash.VerificationFileWriter`** (`hash/VerificationFileWriter.java`) and **`net.filebot.hash.VerificationFormat`/`SfvFormat`** (`format(String path, String hash)`) — `generateVerificationFileContent` should construct a `VerificationFileWriter(PrintWriter, HashType.getFormat(), UTF_8)` and call `.write(path, hash)` per entry instead of hand-building `"path hash\n"` strings (GAP-08). This automatically produces algorithm-correct output (`hash *path` for MD5, `hash ?SHA1*path` for SHA-1, etc.) and the correct 3-line comment header, guaranteeing round-trip compatibility with `VerificationFileReader`/`VerificationUtilities.getHashType` and with external tools.

6. **`net.filebot.hash.VerificationUtilities.EMBEDDED_CHECKSUM`** (`hash/VerificationUtilities.java:20-21`) and **`getEmbeddedChecksum(CharSequence)`** — could be reused server-side (return an extra field on `ChecksumEntryDto`, or compute a `WARNING`-equivalent status) to restore the filename-embedded-checksum highlighting feature described in GAP-12, if that's judged worth porting.

No new hashing/parsing/formatting logic needs to be *written* to close GAP-01/05/06/07/08 — the legacy `net.filebot.hash` package already contains complete, correct, stream-based (64KB buffer, per §3.5) implementations for every one of these behaviors. The current backend's problem is that it does not call into this package at all for computation (items 1-2) and calls into it incorrectly for parsing (item 3), rather than lacking the underlying capability.
