# Subtitles Search & Downloader — Parity Audit

Scope: `specs/05_SUBTITLES_SEARCH_AND_DOWNLOADER.md` vs. legacy Swing (`net.filebot.ui.subtitle.*`, `net.filebot.web.*`, `net.filebot.subtitle.*`) vs. React (`frontend/src/components/SubtitlePanel.tsx`, `frontend/src/api/client.ts`) vs. Spring Boot (`SubtitleController`, `SubtitleServiceImpl`).

---

## 1. Methodology

1. Read `specs/05_SUBTITLES_SEARCH_AND_DOWNLOADER.md` and `specs/00_SYSTEM_ARCHITECTURE_AND_MODELS.md` in full for the intended contract (DTOs, enums, REST endpoints, component tree).
2. Read the legacy Swing implementation end-to-end:
   - `SubtitlePanel.java`, `SubtitlePanelBuilder.java` — top-level panel, language selector, OpenSubtitles login/VIP auth dialog.
   - `SubtitleDropTarget.java` (`Download` / `Upload` inner classes) — the two circular drop targets that launch the auto-match and upload dialogs.
   - `SubtitleAutoMatchDialog.java` — the actual "search + download" workspace (mapping table, per-video subtitle option combo, Subtitle Naming dropdown, Download/Close buttons, hash-matcher vs. name-matcher service panels).
   - `SubtitleUploadDialog.java` (`net.filebot.ui.subtitle.upload`) — upload workflow (video/subtitle/movie/language table, auto-detection, CD-grouping, Upload/Close).
   - `SubtitleDownloadComponent.java`, `SubtitleDropTarget.java`, `SimpleComboBox.java`, `MemoryFileListExportHandler.java` — supporting list/context-menu/export machinery for the older "search-panel" style subtitle browser (double-click/Enter to fetch, right-click context menus for Download / Preview / Save As / Export).
   - `net.filebot.web.OpenSubtitlesHasher`, `OpenSubtitlesClient`, `OpenSubtitlesXmlRpc` (referenced), `ShooterSubtitles`, `VideoHashSubtitleService` — provider/hashing business logic.
   - `net.filebot.subtitle.SubtitleUtilities` (`lookupSubtitlesByHash`, `findSubtitlesByName`, `getBestMatch`, `matchSubtitles`) and `net.filebot.subtitle.SubtitleNaming` — the real "Exact vs. Fuzzy" strategy implementations and the filename-formatting logic.
3. Read the React implementation in full (`SubtitlePanel.tsx`, `frontend/src/api/client.ts`, `frontend/src/types/index.ts`, `GlobalDropZone.tsx`) and grepped the whole `frontend/src` tree for any subtitle upload / preview / auth / context-menu code (`Glob` + `Grep`) — confirmed none exists outside `SubtitlePanel.tsx`.
4. Read the Spring Boot implementation in full (`SubtitleController.java`, `SubtitleServiceImpl.java`, plus the DTO files under `net.filebot.backend.dto`).
5. Cross-referenced each interactive Swing element against React wiring, and each React network call against the Spring Boot service body (not just the interface signature) to detect stub/fake logic.
6. No source files were modified; this is a read-only audit.

## 3. Ambiguous / undocumented JavaFX behavior

1. **`specs/05` Section A's Shooter hash description is inaccurate.** The spec states the algorithm reads "4 blocks ... at positions `5k`, `size/3`, `2*size/3`, and `size-8k` (**8KB each**)". The actual code in `ShooterSubtitles.computeFileHash` (lines 141-162) uses `offset[0] = 4096` (4KB, not 5K) and a `buffer = new byte[4096]` (**4KB blocks, not 8KB**) — only the *last* offset (`fileSize - 8192`) references an 8KB quantity, and only as an offset, not a block size. Any reimplementation based on spec prose alone (rather than the cited source) would produce a hash that never matches Shooter's real server-side hash. Confirmed by reading `ShooterSubtitles.java` directly.
2. **"Exact Search" / "Fuzzy Search" are not literally two buttons in Swing.** They are dialog-internal *service category labels* (`SubtitleServiceBean.getDescription()`), assigned automatically per service type: any `VideoHashSubtitleService` (OpenSubtitles hash lookup, and also Shooter, which also implements `VideoHashSubtitleService`) is labeled "Exact Search" (or its own name, for non-OpenSubtitles hash services) and grouped into the `hashMatcherServicePanel`; any `SubtitleProvider` (name/tag-based search) is unconditionally labeled "Fuzzy Search" and grouped into `nameMatcherServicePanel`. Both run together, automatically, as soon as `startQuery()` is invoked (triggered by dropping video files onto the download drop target) — there is no user-facing manual "Exact" vs. "Fuzzy" toggle in the legacy UI at all. The spec's Section C ("BottomToolbar → LeftControls → ExactSearchButton / FuzzySearchButton") appears to be a UI reinterpretation/invention rather than a faithful transcription of legacy behavior, and the React implementation inherited this invented framing but then wired it to the wrong axis (provider selection instead of hash-vs-name strategy — see G1).
3. **`SubtitleNaming` values vs. React dropdown labels do not match 1:1.** Legacy has exactly 3 values: `ORIGINAL` ("Keep Original"), `MATCH_VIDEO` ("Match Video"), `MATCH_VIDEO_ADD_LANGUAGE_TAG` ("Match Video and Language", the default). React's dropdown (`SubtitlePanel.tsx:354-356`) offers "Match Video and Language", "Original Subtitle Name" (renamed from "Keep Original", and semantically different — legacy `ORIGINAL` keeps the *provider's* subtitle filename verbatim, not a derived "Original Subtitle Name"), and "Language Code Only" (an option that does not exist in `SubtitleNaming` at all — closest legacy analogue is unclear; may be a UI designer's invention). "Match Video" (no language tag) is missing entirely from React. Since the dropdown is non-functional anyway (G5), this is presently cosmetic, but the label set itself needs reconciliation with `SubtitleNaming` if the naming feature is ever implemented.
4. **`OpenSubtitlesHasher` has two independent implementations in the same class** (`computeHash(File)`/`computeHash(InputStream, long)` using `DataInputStream`+manual seeking, vs. `computeHashNIO(File)` using `FileChannel.map`). Both should produce the same hash by construction, but the spec's Section A code excerpt is actually a third, hand-written paraphrase (`ByteBuffer.allocate` + `FileChannel.read`) that doesn't exactly match either real method's code shape (though the underlying math — size + LE-64-bit-sum of head 64K + LE-64-bit-sum of tail 64K — is equivalent). `SubtitleServiceImpl` sidesteps this ambiguity entirely by calling the real `computeHash(File)` method rather than the spec's paraphrase (see G13 / Section 4).

## 4. Reuse opportunities

- **`net.filebot.web.OpenSubtitlesHasher.computeHash(File)`** — already correctly reused by `SubtitleServiceImpl.computeOpenSubtitlesHash` (line 31). No action needed here; this is the model to follow for the rest of the service.
- **`net.filebot.web.OpenSubtitlesClient`** (constructed with `new OpenSubtitlesClient(appName, appVersion)`, or reuse the singleton pattern from `net.filebot.WebServices.OpenSubtitles`) — `SubtitleServiceImpl.searchSubtitles` should call:
  - `OpenSubtitlesClient.getSubtitleListByHash(File[] files, Locale locale)` for the true "Exact/hash" strategy (wraps `computeHash` + `Query.forHash` + XML-RPC `SearchSubtitles`), and
  - `OpenSubtitlesClient.getSubtitleListByTag(File[] files, Locale locale)` (or, to fully match legacy fidelity, `net.filebot.subtitle.SubtitleUtilities.findSubtitlesByName(SubtitleProvider, Collection<File>, Locale, String forceQuery, boolean addOptions, boolean strict)`) for the true "Fuzzy/name" strategy — this is the method that actually implements movie/series auto-detection + `SubtitleMetrics` name-similarity filtering that the spec's "Fuzzy Search" button implies.
  - Both need `OpenSubtitlesClient.login()` called first (anonymous login is fine for search, but VIP login requires the credentials captured by the (currently missing, G7) auth modal via `setUser(username, md5(password))`).
- **`net.filebot.subtitle.SubtitleUtilities.getBestMatch(File, Collection<SubtitleDescriptor>, boolean strict)`** — reuse instead of reimplementing "pick best candidate" logic; used by legacy to rank hash-search results before showing them to the user.
- **`net.filebot.web.ShooterSubtitles`** (`getSubtitleList(File[], Locale)`, and its private `computeFileHash(File)` 4-block-MD5 algorithm) — currently entirely unused by Spring Boot (G3). Should be called directly (or its package-private `computeFileHash`/`md5` helpers exposed) rather than reimplemented, both to fix G3 and to avoid the 8KB-vs-4KB block-size discrepancy documented in Section 3.1. Note `ShooterSubtitles.getSubtitleList` only supports `Locale.CHINESE`/`Locale.ENGLISH` (throws `IllegalArgumentException` otherwise) — this constraint must be surfaced to the frontend/DTO layer if wired up (currently `LanguageCode` allows 16 languages with no Shooter-specific restriction).
- **`net.filebot.subtitle.SubtitleUtilities.fetchSubtitle(SubtitleDescriptor)`** — real byte-fetching + archive-extraction (`ArchiveType.forName(descriptor.getType())`) logic that `SubtitleServiceImpl.downloadSubtitles` needs to actually retrieve subtitle content (fixes G4); currently the service never calls anything like this.
- **`net.filebot.subtitle.SubtitleNaming`** (`format(File video, SubtitleDescriptor subtitle, String ext)`, values `ORIGINAL` / `MATCH_VIDEO` / `MATCH_VIDEO_ADD_LANGUAGE_TAG`) — should back a new field on `SubtitleDownloadRequestDto` (or a batch-level naming parameter) and be called to compute the destination `File` the same way `SubtitleAutoMatchDialog.DownloadTask.getDestination` does (`new File(video.getParentFile(), name)`), fixing G5.
- **`net.filebot.util.FileUtilities.writeFile(ByteBuffer, File)`** — the actual disk-write primitive used by legacy `DownloadTask.doInBackground` (line 877) and `SubtitleDownloadComponent.save`/`.export`; `SubtitleServiceImpl.downloadSubtitles` should call this (via `fetchSubtitle(...).getData()`) instead of doing string manipulation on the path.
- **`OpenSubtitlesClient.checkSubtitle` / `.uploadSubtitle` / `.detectLanguage`** — needed to implement G6 (upload flow) faithfully: `checkSubtitle` mirrors `SubtitleUploadDialog.runCheck`'s "does this subtitle already exist in the DB" check, `detectLanguage` mirrors its language auto-detection fallback, and `uploadSubtitle(identity, locale, videoFiles, subtitleFiles)` is the real upload call that `SubtitleServiceImpl.uploadSubtitle` should delegate to instead of no-op'ing.
