# Settings & Preferences — Parity Audit

## 1. Methodology

Read in full: `net/filebot/Settings.java`, `net/filebot/util/prefs/{FilePreferences,FilePreferencesFactory,PropertyFileBackingStore}.java`, `net/filebot/util/SystemProperty.java`, `net/filebot/ui/SupportDialog.java`, `net/filebot/License.java` (skim, size-checked), `net/filebot/LicenseModel.java` (skim, size-checked), plus grep across `net/filebot/**` for every `Settings.forPackage(...).entry(...)` call site to recover the *actual* scattered preference-key catalog (there is no single legacy "settings schema" class — `Settings.java` is an app-metadata/Preferences-factory helper, not a settings DTO). Cross-referenced against `frontend/src/components/SettingsPanel.tsx`, `SettingsController.java`, `SettingsServiceImpl.java` (both read in full), and the already-loaded `specs/09_SETTINGS_AND_PREFERENCES.md`, `AppShell.tsx`.

Key structural finding up front: **the legacy app has no centralized "Settings" concept at all.** Each panel/class persists its own preferences under its own package-scoped `Preferences` node (e.g. `net/filebot/ui/rename` for `RenamePanel`, `net/filebot` for `Settings`/`SupportDialog`/`Main`). Spec 09's `AppSettingsDto` is a **synthesized abstraction invented for the port** — it does not correspond to any single legacy class. That's a legitimate design choice for a web app, but the audit below checks whether the synthesized model still round-trips the *values* correctly (same keys, same node, same defaults) — it currently does not.

## 3. Ambiguous / undocumented JavaFX behavior

- **License subsystem (S-9)**: whether license enforcement should be ported, dropped, or replaced with something else (e.g. a simple "this is a self-hosted build" notice) is a product decision, not something inferable from code. Do not build a License settings screen without an explicit decision.
- **`ui.theme` / `ui.language` (S-11)**: could not confirm these preference keys exist anywhere in the legacy source actually audited by this fork. A full-repository grep for `.theme` / `.language` / `Locale` usage outside the files listed in this fork's directive is needed before trusting spec 09's claim that they exist as real legacy preferences.
- **"Anime Format" 4th slot (S-12)**: needs confirmation from whoever owns the Rename Workspace / `RenameModel.Mode` enum audit — is there a distinct Anime mode anywhere in the matcher logic, or was "Anime Format" simply invented by the spec author by analogy with `MatchingMode.ANIME` (which exists in `specs/00`'s enum) without verifying it maps to a real 4th persisted format key?
- **Was there ever a real "reset settings" UI button in Swing (S-8)?** `Settings.clear()` is a library method with no located caller. It's possible such a button exists in a Swing dialog not covered by this fork's file list (e.g. buried in a preferences dialog not referenced by `Settings.java`/`SupportDialog.java`) — recommend a targeted grep for `.clear()` call sites app-wide before concluding it's spec-invented.

## 4. Reuse opportunities

1. **Directly reuse `net.filebot.util.prefs.FilePreferencesFactory` + `PropertyFileBackingStore` + `FilePreferences`** (3 small, dependency-free classes, already on the backend's classpath since they're in `src/main/java/net/filebot/...`) instead of raw `java.util.prefs.Preferences.userNodeForPackage(...)`. Wire it up by setting the `java.util.prefs.PreferencesFactory` system property to `net.filebot.util.prefs.FilePreferencesFactory` and `net.filebot.util.prefs.file` to a stable path under the app's data directory, ideally *before* Spring context startup (e.g. in `FileBotBackendApplication.main()` or via `SPRING_APPLICATION_JSON`/JVM args from `desktop-wrapper/main.js`'s `spawn(...)` call). This closes S-2 with near-zero new code and — combined with fixing S-1/S-3's node/key names to match `RenamePanel`'s actual `net/filebot/ui/rename` node and `rename.format.*`/`rename.language` keys — would make the new Settings screen genuinely read a real legacy `prefs.properties` file if one is migrated in from an existing install.
2. **`net.filebot.Settings.forPackage(Class)` / `.entry(String)` pattern** is a thin, reusable wrapper already used consistently across the legacy codebase; `SettingsServiceImpl` could construct one `Settings` instance per logical settings group (`Settings.forPackage(RenamePanel.class)` for formats/language, `Settings.forPackage(Settings.class)` for app-level flags) to guarantee exact node-path parity with the legacy panels instead of re-inventing a flat single-node schema.
3. If provider credential encryption (S-7) is implemented, there is no existing crypto utility for this in the audited files — `net.filebot.util.PGP` exists (referenced by `Settings.java:5` import, used for license clear-sign verification) but is a signature-verification utility, not a general-purpose symmetric encryption-at-rest helper; a new solution (e.g. OS keychain integration via Electron's `safeStorage`, passed through to the backend) would need to be designed, not ported.
