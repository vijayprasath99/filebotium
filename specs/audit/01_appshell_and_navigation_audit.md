# App Shell, Navigation, Global DnD & List Panel — Parity Audit

Audited directly by the lead auditor (not delegated), because these findings are cross-cutting and needed early to scope the other per-area audits correctly.

## 1. Methodology

Read in full: `src/main/java/net/filebot/ui/MainFrame.java`, `FileBotMenuBar.java`, `HeaderPanel.java`, `NotificationHandler.java`, `SinglePanelFrame.java`, `PanelBuilder.java`, `GettingStartedStage.java`, `SupportDialog.java`, `ui/list/ListPanel.java`, `ui/list/ListPanelBuilder.java`, `ui/transfer/DefaultTransferHandler.java`, `ui/transfer/DefaultClipboardHandler.java`, `Main.java` (startup/shutdown lifecycle), plus the backend `AppShellController.java`, `websocket/WebSocketConfig.java`, `websocket/TaskProgressPublisher.java`, and every frontend shared file (`AppShell.tsx`, `SidebarNav.tsx`, `GlobalDropZone.tsx`, `DevLogsModal.tsx`, `api/client.ts`, `api/websocketClient.ts`, `types/index.ts`, `utils/fileUtils.ts`). Grepped for `AppShellService`/`SimpMessagingTemplate`/`convertAndSend` usage across the whole backend to determine whether anything actually publishes to the WebSocket topics the spec promises. Cross-referenced `PanelBuilder.defaultSequence()` (the ground-truth list of top-level legacy tabs) against `SidebarNav.tsx`'s tab array.

**Terminology correction for the audit report:** The legacy application's primary UI toolkit is **Java Swing** (`javax.swing.*`, `MigLayout`), not JavaFX. A single JavaFX `WebView` island (`GettingStartedStage.java`) is embedded only for the onboarding/help screen. All "JavaFX" gap references throughout this audit (per the requested terminology) refer to this Swing codebase unless explicitly noted as the JavaFX WebView island.

## 3. Ambiguous / undocumented legacy behavior requiring a product decision (not guessed at)

1. **GroovyPad (`F5`)** — an interactive Groovy scripting console with full JVM access, launched from the main window. Porting this as-is to a network-exposed Spring Boot service would be a significant remote-code-execution surface. Recommend the product owner explicitly decide "drop" vs. "sandbox and port" rather than the audit assuming either way. Not included as an actionable implementation-plan task pending that decision.
2. **`SupportDialog.AppStoreReview`** — tied to Mac App Store distribution (`isAppStore()`), which is out of scope for the documented Electron-only packaging strategy (specs/10). Flagging for explicit "won't implement" sign-off rather than silent omission.
3. **Intake response envelope mismatch (AS-8)** — the spec (01 §B) and the actual frontend/backend contract for `/api/v1/app/intake` disagree with each other (envelope vs. flat array). Since frontend and backend already agree with each other, it's ambiguous whether the *spec* is wrong (should be updated to flat array) or the *implementation* is wrong (should add the envelope + finally implement recursive/hidden-file filtering, which needs somewhere to report `rejectedCount`). The audit recommends the latter (implementation should catch up to spec) since the envelope is the only way to communicate filtered/rejected file counts back to the user, but this is a product/spec decision, not purely technical.

## 4. Reuse opportunities

- `AppShellController.processFileIntake` should reuse `net.filebot.util.FileUtilities` (already imported project-wide, e.g. `getChildren(File, FileFilter)` used in `Main.java:88`) for recursive directory expansion, and should reuse the legacy hidden/system-file filter logic (grep `net.filebot.util.FileUtilities` for existing `SYSTEM_FILES`/hidden-file predicates before writing a new one — the legacy DnD pipeline in `ui/transfer/FileTransferablePolicy.java`/`BackgroundFileTransferablePolicy.java` almost certainly already has this exact filter; the Analyze/Filter-area auditor's `FileTreeTransferablePolicy.java` read should confirm the exact predicate to port verbatim).
- A real `AppShellService` (currently entirely absent — the controller does file I/O inline) should be introduced per the spec's own Section B interface, both for testability and so `handleClipboardContent` can actually be implemented.
- For AS-1/AS-2 (dead WebSocket publisher / unrouted notifications), the fix is infrastructural rather than "port more Java": inject `SimpMessagingTemplate` into `TaskProgressPublisher` and call `.convertAndSend(topic, dto)`, then have `NotificationHandler`'s pattern (any service-layer warning/error) mirrored by a small `@Component` that listens for a Spring `ApplicationEvent` (or is called directly by services on caught exceptions) and forwards to `/topic/notifications`. This is new Spring plumbing, not a Java-to-Java port, but should be listed as foundational (blocks real fixes in Rename/SFV progress UX).
