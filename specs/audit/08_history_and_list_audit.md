## 3. Ambiguous / undocumented JavaFX behavior

1. **Spec Section A's per-action rollback rules do not correspond to any stored data.** The spec states MOVE/COPY/HARDLINK/SYMLINK each have distinct reversal rules, and that MOVE-rollback additionally "deletes empty parent directories of `to` if empty." In the actual code, `History.Element` (`History.java` L76-125) has **no action-type field** — only `dir`, `from`, `to`. `StandardRenameAction.revert(File current, File original)` (`StandardRenameAction.java` L193-237) determines what to do purely from **live filesystem inspection** at revert time (existence, symlink-ness, regular-file-ness, directory-ness of the two paths) — it does not know or care what `StandardRenameAction` originally created the entry. There is also **no empty-parent-directory cleanup logic anywhere in `revert()`** — it only ever calls `moveRename(...)` or `trash(...)` on the two paths directly involved; no directory listing/deletion of parents was found in this method or its call sites in `HistoryDialog.RevertAction.revert()` (L569-606). Whether such cleanup exists elsewhere (e.g. inside `moveRename`/`FileUtilities`) was not traced as part of this audit's scope (those files are outside the assigned Section A source list) — but nothing in the assigned History-area files performs it. **Recommendation for the audit report: spec Section A should be corrected to describe the actual filesystem-state-based dispatch in `StandardRenameAction.revert()`, not an action-type-based rule table**, since no such rule table exists in the codebase.
2. **"Clear History" has no legacy equivalent.** A full inventory of `HistoryDialog`'s interactive elements — `JButton`(`importAction`/`Import` L142, `Export` L144, `RevertCurrentSelectionAction`/`Revert Selection` L147, `closeAction`/`Close` L148), `createImageButton(clearFilterAction)` (L133, clears the *filter text box*, not the history log), `JPopupMenu` with `RevertSelectionAction`/`Revert...` (L412-413) — contains **no "Clear History" / "Delete History" / "Purge Log" action anywhere**. Section A's UI-hierarchy bullet "Clear History: Purges persistent transaction logs" (spec line 18) does not correspond to any button, menu item, or action listener found in `HistoryDialog.java` or `HistoryPanel.java`. This appears to be a spec-authoring invention (possibly extrapolated from the presence of `HistorySpooler.commit()`/file-truncation internals, which are implementation details never exposed as a user-facing "clear" command in legacy). Confirmed via full-file read plus the `HistoryDialog` inventory above.
3. **Import History (drag-and-drop of `.xml` files) has no React/Spring equivalent and is out of the spec's Section A/B/C entirely.** `HistoryDialog.importHandler` (L646-681) lets a user drag a `.xml` history file onto the dialog to merge it into `HistorySpooler`'s session history (`HistorySpooler.append(History.importHistory(...))`, then refreshes the view via `getCompleteHistory()`). Since the spec itself never mentions Import, this is not scored as a Gap ID in Section 2 above (out of spec scope), but is called out here because a complete parity effort would need it, and because `HistorySpooler.append(History)` (L135-137, the merge-by-value overload) is a ready-made reuse target (see Section 4).
4. **`StandardRenameAction.canRevert()` gating is undocumented in the spec.** `CmdlineOperations.writeHistory()` (L911-916) only calls `HistorySpooler.append(...)` `if (action.canRevert())` — and `StandardRenameAction.TEST` (L124-135) overrides `canRevert()` to return `false`. This means "dry run"/test actions are deliberately excluded from history. It was not possible in the time available to trace every `RenameAction.canRevert()` implementer to confirm which of MOVE/COPY/KEEPLINK/SYMLINK/HARDLINK/CLONE/DUPLICATE return `true` vs `false` beyond the default (`StandardRenameAction` does not override `canRevert()` for any case except `TEST`, so the interface's default applies to the rest — the default was not located within the audited file set). Any eventual fix for Gap 3 (wiring `RenameWorkspaceServiceImpl` to `HistorySpooler`) should replicate this `canRevert()` gate rather than unconditionally appending every rename.

## 4. Reuse opportunities

Spring Boot should link against and delegate to these existing legacy classes directly rather than re-implementing history persistence/export, to guarantee on-disk compatibility with the legacy desktop app and the CLI sharing the same `~/.filebot` profile:

1. **`net.filebot.HistorySpooler` (singleton, already imported by `HistoryServiceImpl`) — use its full API, not just the read path:**
   - `HistorySpooler.getInstance().append(Map<File, File> elements)` / `append(Iterable<Entry<File,File>> elements)` (`HistorySpooler.java` L113-127) — **this is the exact call `RenameWorkspaceServiceImpl` is missing (Gap 3).** After a successful batch rename at `RenameWorkspaceServiceImpl.java` L172, build the same `from → to` map already computed there and call `HistorySpooler.getInstance().append(renameMap.entrySet())`, mirroring `CmdlineOperations.writeHistory()` (L911-916), including the `action.canRevert()` gate (Section 3, item 4).
   - `HistorySpooler.getInstance().commit()` (L66-111) — already correctly relied on implicitly via the JVM shutdown hook (L28-34) for the read path (`getCompleteHistory()` reads both the on-disk file and any uncommitted in-memory `sessionHistory`), but if the Spring Boot process runs long-lived (unlike the CLI's short-lived process), consider calling `commit()` explicitly after each rename batch or on a timer so `history.xml` is durably updated even if the backend process is killed abnormally (Electron force-quit, crash) rather than relying solely on the shutdown hook.
   - `HistorySpooler.getInstance().getCompleteHistory()` (L44-64) — **already correctly reused** by `HistoryServiceImpl.getTransactionHistory()` (L29) and `exportHistory()` (L107). This is a solid reuse pattern; keep it.
   - There is **no `HistorySpooler` method to delete/clear the persistent file** — `clearHistory()` (Gap 4) cannot be implemented by calling an existing spooler method; it requires either (a) adding a new method to `HistorySpooler` (e.g. `clearPersistentHistory()` that acquires the same `FileLock` used by `commit()`/`getCompleteHistory()` and truncates/deletes `persistentHistoryFile`), done in the shared `net.filebot` module so both the legacy app and the backend see a consistent implementation, or (b) directly truncating `ApplicationFolder.AppData.resolve("history.xml")` under a `FileLock` from `HistoryServiceImpl` itself, replicating the locking pattern already used in `commit()` (L72-107). Given legacy has no "clear" feature at all (Section 3, item 2), this needs a product decision, not just an engineering fix.
   - `HistorySpooler.getInstance().append(History importHistory)` (L135-137, merge overload) — ready-made for an eventual "Import History" feature (Section 3, item 3) if that gets added to the React spec later.

2. **`net.filebot.History.exportHistory(History, OutputStream)` / `History.importHistory(InputStream)`** (`History.java` L197-217) — JAXB marshal/unmarshal against the real `@XmlRootElement(name="history")` schema. `HistoryServiceImpl.exportHistory()` already calls `History.exportHistory(...)` correctly for the XML case (L107-113) — **the fix for Gap 5 is not to reuse more Java code, but to stop the React side from re-implementing its own XML serializer** (`HistoryPanel.tsx` L62-83) and instead stream/download the bytes the backend already produces via `History.exportHistory(...)`, e.g. by changing the export endpoint to return the file as a `ResponseEntity<byte[]>`/`StreamingResponseBody` with `Content-Disposition: attachment` instead of writing to an opaque server-side `outputPath`, and having `handleExportHistory` in React save that response directly via Blob instead of hand-building XML. This also fixes the "exported file isn't re-importable by legacy" defect noted in Gap 5, since it would emit the exact same JAXB output legacy itself produces.
3. **Real on-disk XML schema (from `History.java`'s JAXB annotations — use this to correct spec Section A, which currently documents a schema that does not match the code):**
   ```xml
   <history>
     <sequence date="EEE MMM dd HH:mm:ss zzz yyyy">   <!-- java.util.Date default JAXB format; no "count" attribute exists -->
       <rename dir="/absolute/parent/dir" from="original-filename.ext" to="new/relative/or/absolute/path.ext" />
       <!-- repeated <rename> elements, NOT <element> -->
     </sequence>
   </history>
   ```
   Key corrections versus spec line 24 (`<history><sequence date="..." count="..."><element from="..." to="..."/></sequence></history>`): the per-item tag is `<rename>` not `<element>`; `<rename>` carries a required `dir` attribute the spec omits; `<sequence>` has no `count` attribute. Both `HistoryServiceImpl` (via `History.exportHistory`) and any future frontend consumer must key off `rename`/`dir`/`from`/`to`, not the spec's literal text, to stay byte-compatible with files the legacy app and CLI already write/read at `~/.filebot/history.xml` (`ApplicationFolder.AppData.resolve("history.xml")`, `HistorySpooler.java` L36).
4. **`net.filebot.StandardRenameAction.revert(File current, File original)`** (`StandardRenameAction.java` L193-237) — this is the exact, already-battle-tested reversal engine `HistoryServiceImpl.rollbackTransaction()` should call per target path (Gap 2) instead of its current `file.exists()` stub. It already handles the MOVE/COPY/HARDLINK/SYMLINK/KEEPLINK distinctions the spec asks for, purely from filesystem state — no schema change needed. Backend usage would look like: for each `(from, to)` pair resolved out of the transaction's elements (using `History.getRenameMap()`, L182-195, or the equivalent resolution logic already in `HistoryDialog.RevertAction.getRenameMap()` L608-629, which correctly re-resolves relative `to` paths against `element.dir()`), call `StandardRenameAction.revert(new File(to), new File(from))`, catch `IOException`/`IllegalArgumentException` per-element to populate `RollbackErrorDto`, and count successes/failures accordingly — this single reuse closes both Gap 2 and gives correct per-action-type behavior "for free" without needing to persist an action field at all (consistent with Section 3, item 1's finding that legacy itself never persists action type).
5. **`History.getRenameMap()`** (`History.java` L182-195) — already does the `to`-path-is-relative-or-absolute resolution logic that `HistoryServiceImpl.getTransactionHistory()` currently reimplements inline (L38-42, `if (!to.isAbsolute()) to = new File(element.dir(), element.to())`). Minor duplication; could be replaced by calling `getRenameMap()` directly on the per-sequence data, though the current inline logic is at least *consistent* with the original (no divergence found here).
