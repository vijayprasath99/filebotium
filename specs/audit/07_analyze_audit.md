# Audit: Analyze Panel & MediaInfo Inspector (specs/07)

## 1. Methodology

Read the full legacy Swing source for `net.filebot.ui.filter` (`FilterPanel`, `FilterPanelBuilder`,
`FileTreePanel`, `FileTree`, `FileTreeCellRenderer`, `FileTreeExportHandler`, `FileTreeTransferablePolicy`,
`Tool`, `MediaInfoTool`, `AttributeTool`, `TypeTool`, `ExtractTool`, `SplitTool`) plus every class it directly
depends on for business logic: `net.filebot.mediainfo.MediaInfo` / `MediaInfoLibrary` / `MediaInfoException`
(native JNA binding), `net.filebot.media.MediaCharacteristicsParser` / `MediaCharacteristics` / `FFProbe`
(fallback parser), `net.filebot.archive.ArchiveExtractor` / `Archive`, `net.filebot.MetaAttributeView`,
`net.filebot.media.MetaAttributes`, `net.filebot.UserFiles` (reveal/trash), and `net.filebot.ui.PanelBuilder`
(`fileHandlerSequence()`, `defaultSequence()`). Cross-referenced every `JButton` / `JMenuItem` / `JPopupMenu` /
`Action` / `addActionListener` found in the `ui/filter` package against the current React implementation
(`frontend/src/components/AnalyzePanel.tsx`, read in full) and its dependencies (`frontend/src/api/client.ts`,
`frontend/src/types/index.ts`, `frontend/src/utils/fileUtils.ts`, `frontend/src/components/AppShell.tsx`,
`frontend/src/components/GlobalDropZone.tsx`), and against the Spring Boot surface
(`AnalyzeController.java`, `MediaInfoInspectorServiceImpl.java`, `MediaInfoInspectorDto.java`,
`AppShellController.java`, `MediaFileDto.java`, `AnalysisTool.java`, `build.gradle`), all read in full. Also
inspected `desktop-wrapper/preload.js` and `desktop-wrapper/main.js` for any Electron IPC bridge relevant to
OS shell integration (reveal-in-folder, trash).

Note on terminology: the legacy Filter/Analyze panel (and the whole desktop shell) is **Java Swing**, not
JavaFX — the task brief's "JavaFX" framing is a misnomer for this codebase; the only actual JavaFX code in the
entire legacy app is the embedded `WebView` in `GettingStartedStage.java` (App Shell area, out of scope here).
All "JavaFX source" table cells below refer to the real Swing sources.

## 3. Ambiguous / Undocumented Legacy Behavior

- **RESOLVED (not ambiguous):** `PanelBuilder.fileHandlerSequence()` (`ui/PanelBuilder.java:35-39`) returns exactly `[RenamePanelBuilder, SfvPanelBuilder, ListPanelBuilder]` — i.e. "Rename", "SFV", "List" in that order. This matches React's hardcoded 3-item "Send to" submenu (`AnalyzePanel.tsx:475-494`) exactly, both in membership and order. No gap here beyond the List-routing defect already captured as AN-12.
- `ExtractTool.extractAction` always passes `ConflictAction.AUTO` and `forceExtractAll = true` to `ExtractWorker` — there is no UI to choose "extract selected entries only" vs. "extract all", even though the underlying worker supports a `filter`/partial-selection extraction mode (`ExtractWorker.call`, the `filter`/`selection` branches). Confirm this is intentional legacy behavior (i.e. the "Extract All" button is the *only* extraction affordance in the Swing UI) before treating partial-entry extraction as in-scope for the port; if it's out of scope, AN-1's target backend surface only needs "list + extract all", not per-entry selection.
- `SplitTool` only ever *previews* a size-based grouping (`Disk 1`, `Disk 2`, ..., `Remainder`) — there is no action anywhere in `SplitTool.java` that physically splits, copies, or moves files into those groups; the only way files "leave" this tool is via drag-export (`FileTreeExportHandler`, `tree.setDragEnabled(true)`) onto an OS file manager. Confirm with the product owner whether "Parts" is meant to stay preview-+ drag-export-only in the port (matching legacy exactly) rather than implying an actual server-side file-splitting/copy operation.
- `AttributeTool` only lists files that already carry FileBot-written metadata (`xattr.getMetaInfo(file)` returns non-null and is an `Episode`/`Movie` with a resolvable provider ID) — files with no prior rename history are silently excluded from the table entirely (not shown as empty rows). This is a meaningful behavioral nuance for AN-3's backend implementation: the endpoint should omit files with no xattr metadata rather than returning empty-string placeholders for them.
- `MediaInfoTool`'s comparison table exposes **every** raw MediaInfo key MediaInfo itself reports (via `mi.snapshot()`, no filtering) — including obscure/vendor-specific keys not in the DTO's fixed schema (`Codec/Extensions`, `Format_Profile`, `Encoded_Library`, `ColorSpace`, `ChromaSubsampling`, etc., depending on the file). The backend DTO (spec §B) intentionally curates a fixed subset; confirm this curation is an accepted, deliberate simplification of the port rather than a gap (it does mean advanced users lose access to the full raw property inspection legacy offered — related to AN-7's lost comparison view).

## 4. Reuse Opportunities

- `MediaInfoInspectorServiceImpl` already correctly reuses `net.filebot.mediainfo.MediaInfo` (real JNA binding to `libmediainfo`, same class the legacy Swing `MediaInfoTool` uses via `mi.snapshot()`) — this is genuine native metadata extraction, not a stub; `build.gradle:90-92` confirms `net.java.dev.jna:jna` / `jna-platform` are on the classpath. Keep this pattern. Extend it to also read `HDR_Format` / `HDR_Format_Compatibility` MediaInfo keys directly for `hdrFormat` instead of repurposing `colour_primaries` (AN-8), and optionally expose the raw `mi.snapshot()` key/value map (not just the fixed field subset) via a new endpoint to support restoring the AN-7 comparison UX.
- Fix AN-9 by catching `MediaInfoException` specifically (before the generic `catch (Exception e)`) inside `MediaInfoInspectorServiceImpl.inspectFile` and surfacing its message (already purpose-built: `"Unable to load <arch> (<bit>) native library <libname>: <cause>"`, `MediaInfoException.java:15-24`) through a distinct DTO field or HTTP status, so the frontend can render spec §D's "Missing Native MediaInfo Library Warning" instead of a generic empty state.
- AN-4 (Types) should call `net.filebot.media.MediaDetection.isMovie` / `isEpisode` / `getDiskFolderFilter()` / `getClutterFileFilter()` / `getClutterTypeFilter()` and `net.filebot.MediaTypes` (`VIDEO_FILES`, `SUBTITLE_FILES`, `AUDIO_FILES`, `ARCHIVE_FILES`, `VERIFICATION_FILES`) server-side, ported straight from `TypeTool.getMetaTypes()` (`ui/filter/TypeTool.java:85-98`) — this is pure classification logic with no Swing dependency and can be lifted almost verbatim into a new `analyzeService.classifyTypes(paths)` method returning group name → file list + total size.
- AN-1 (Archives) should reuse `net.filebot.archive.Archive` (`Archive.open`, `listFiles()`, `extract(File)`, `extract(File, FileFilter)`) and `net.filebot.archive.FileMapper` directly — this logic has zero Swing/UI dependency in `ExtractTool`'s model-building code (only `ExtractWorker`'s progress callbacks are Swing-flavored `ProgressWorker`, which should be replaced with the async/WebSocket progress plumbing per `specs/00_SYSTEM_ARCHITECTURE_AND_MODELS.md` §4-5 once a real task-progress publisher exists on the backend).
- AN-2 (Parts) should port `SplitTool.createModelInBackground`'s bin-packing loop verbatim (`ui/filter/SplitTool.java:71-122`) — it is plain `File`/`long` arithmetic with no Swing types involved except the `TreeNode`/`FolderNode` model it builds, which trivially maps to a JSON group-list DTO.
- AN-3 (Attributes) should reuse `net.filebot.media.XattrMetaInfo` (`xattr.getMetaInfo(file)`, `xattr.getOriginalName(file)`) and/or `net.filebot.media.MetaAttributes`/`net.filebot.MetaAttributeView` directly in a new service method — `MetaAttributeView` already resolves the correct platform-specific xattr backend (`DefaultXattrView` on Windows/Linux, `MacXattrView` on macOS, `ExtAttrView` on BSD), so this is a thin, low-risk wrapper. This is exactly the metadata FileBot itself writes during rename execution (see the Rename Workspace area's audit for where it's written via `MetaAttributes.setObject`/`setOriginalName`), so round-tripping it here is high-value reuse. It would also finally populate the currently-always-empty `MediaFileDto.xattrs` field (`AppShellController.java:56`) that the shared domain model (`specs/00...md` §3.1) already specs but nothing implements.

**Summary counts:** 12 real gaps (AN-1 through AN-12, excluding the resolved AN-11 ambiguity note and the AN-13 spec-doc-only defect) — 5 BROKEN_FUNCTIONALITY (AN-1, AN-2, AN-3, AN-4, AN-5, AN-12 — six, see table), 2 DATA_INTEGRITY_RISK (AN-8, AN-9), 1 COSMETIC (AN-7), 2 MINOR (AN-6, AN-10), 1 informational (AN-11's residual note). The single highest-impact finding is that **three of five tool tabs (Archives/Extract, Parts/Split, Attributes/xattr) are entirely disconnected from any backend logic** — they render plausible-looking but functionally fake, client-side-only data — while the MediaInfo tab itself is a genuine, correctly-wired native-library integration with only labeling (AN-8) and error-reporting (AN-9) defects.
